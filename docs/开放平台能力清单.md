# 开放平台能力清单

本文档回答一个问题：**知乎开放平台给我们提供了哪些能力，每项能力能做什么、不能做什么。** 写功能方案、排优先级、估额度预算时，以本文为准；端点参数与响应字段的完整定义见 [content-api.md](content-api.md)、[user-data-api.md](user-data-api.md)、[knowledge-api.md](knowledge-api.md)、[quota-api.md](quota-api.md)、[oauth.md](oauth.md)、[mcp.md](mcp.md)、[hackathon-content-api.md](hackathon-content-api.md)。

额度数据来自 2026-09-12 用真实 Access Secret 调用 `/api/v1/quota` 的实测结果；契约状态标注了「有契约文档」和「仅开通、无契约」两种，后者端点未知，调用前必须先探明，不允许猜路径消耗额度。

## 一、通用约定

- Base URL：`https://developer.zhihu.com`（OAuth 换 token 在 `https://openapi.zhihu.com`）。
- 鉴权：所有业务请求带 `Authorization: Bearer <access_secret>` 和秒级时间戳头 `X-Request-Timestamp`。Access Secret 只存服务端，不进前端。
- 参数为 PascalCase（如 `Query`、`Count`）；响应外壳统一为 `{ Code, Message, Data }`，`Code=0` 为成功。
- 错误码约定：`10001` 参数错误、`20001` 鉴权失败、`30001` 频率限制、`30002` 额度耗尽、`90001` 请求失败；知识库另有 `40004/40005/40006/50002` 等业务码。
- 额度模型：按账号汇总、当日有效，多个 Access Secret 共享同一额度池；`/api/v1/quota` 查询本身不耗额度。额度耗尽后该账号下所有 Secret 都不能再用该项能力。
- 个人数据类接口必须在请求中携带当前用户的 OAuth token；缺失 token 时服务端拒绝请求，不能回落到开发者本人身份。

## 三、各项能力详解

### 1. 知乎搜索 `zhihu_search`

- 端点：`GET /api/v1/content/zhihu_search`，参数 `Query`（必填）、`Count`（默认 10，最大 10）。
- 提供：知乎站内问题/回答/文章的标题、类型（`Answer`/`Article`）、内容摘要 `ContentText`（实测 300-1000+ 字，信息量大）、原文链接（自带 utm 溯源参数）、作者昵称与认证、赞同数、评论数、权威等级、相关性排序分，部分结果带精选评论。
- 能做什么：一切"围绕一个问题找证据"的场景——研究简报取数、众声取数、按关键词找不同立场的作者、验证某个说法在知乎的讨论情况。
- 边界：`HasMore` 当前固定 false，**不支持翻页**，一次最多 10 条；`ContentText` 是摘要不是全文；额度虽宽裕也不要在自动重试里放大调用量。

### 2. 全网搜索 `global_search`

- 端点：`GET /api/v1/content/global_search`，参数 `Query`（必填）、`Count`（最大 20）、`SearchDB`（`all`/`realtime`/`static`）、`Filter`（高级过滤表达式）。
- 提供：知乎站外网页结果，字段与知乎搜索基本一致，摘要中命中词用 `<em>` 高亮。
- 能做什么：研究简报的补充证据面（站内讨论 + 站外文档/报告对照）、`Filter` 支持按域名和发布时间过滤，可做"最近一个月的外部报道"这类时间约束检索。
- 边界：`Filter` 的 host 条件**不支持知乎域名**（查知乎用知乎搜索）；实测对中文知识管理类查询返回结果里混有知乎站内链接，索引口径需在使用中继续确认。

### 3. 知乎热榜 `hot_list`

- 端点：`GET /api/v1/content/hot_list`，参数 `Limit`（默认 30，最大 30）。
- 提供：当前热榜问题/文章列表，每条含标题、知乎链接（问题页）、缩略图、摘要（部分条目无摘要）。
- 能做什么：首页的问题种子（"今天值得弄明白什么"）、热榜与用户兴趣的规则关联候选、结合自身快照积累做"昨天到今天的热点变化"。
- 边界：**没有热度值和官方涨跌字段**，列表顺序只代表本次返回顺序，界面不得编造"暴涨/爆了"；一次调用整榜返回，每 100 次/天的额度靠服务端共享缓存（1 小时刷新、并发合并）撑住，本地与桌面运行面另做落盘，重启后仍能显示上一批真实获取过的内容。上游失败或额度耗尽时保留上一批并标注真实获取时间，没有缓存可回退时如实报错，不用空白或示例内容掩盖。

### 4. 知乎直答 `zhida_openai`

- 端点：`POST /v1/chat/completions`，OpenAI 兼容形态，参数 `model`、`messages`、`stream`。
- 三档模型：`zhida-fast-1p5`（快速归纳，最省额度）、`zhida-thinking-1p5`（深度思考，响应含 `reasoning_content`）、`zhida-agent`（内置检索增强）。
- 提供：基于知乎内容的生成式回答，支持流式 SSE（`data: [DONE]` 结束，含心跳）。
- 能做什么：结构化整理类任务——众声的立场聚类（已验证：给编号来源 + JSON 输出指令，能稳定返回可解析结果且引用编号有效）、摘要生成、问题改写、简报润色。
- 边界：直答返回**生成内容**，不返回具体答主和原始条目，需要可溯源证据时必须用搜索接口而不是直答；其他 OpenAI 参数（temperature 等）不保证生效；相同输入应走缓存并优先 fast 档。

### 5. 问题回答 `question_answers`

- 端点：`GET /api/v1/content/question_answers`，参数 `QuestionUrl`（必填，知乎问题完整 URL）、`Limit`（1–50，默认 20）、`Offset`。契约由官方 zhihu-cli 的 `capabilities` 探明并实测验证。
- 提供：指定问题下回答的 `ContentToken`、`ContentType`、`Summary`（内容摘要，150–300 字，非全文）、`Url`；`Paging.IsEnd`/`NextOffset` 支持翻页。
- 能做什么：**众声的落点来源**——把"同一问题下不同说法"落到实处。搜索给出议题的聚焦问题后，这里直读该问题下的真实回答，比跨问题检索更贴合"同一个问题大家都在吵什么"。
- 边界：**不返回作者名、赞同数、评论数**（与搜索接口不同），因此这些来源在界面上只能呈现摘要与链接，不得编造互动数据；额度仅 100 次/天，只在已判定聚焦问题时调用，并有 15 分钟缓存，不进自动链路。

### 6. 创作能力 `creator`（已开通，无契约）

- 现状：额度接口确认存在（100 次/天），无契约。
- 推测能力（以黑客松能力表为准）：本人创作全文、评论、账号统计、单篇统计。
- 对产品的价值（探明契约后）："我的创作进研究"——用户自己的回答是全文（别人的内容只有摘要），可把用户在某个问题上的既有立场与检索到的观点对照；创作复盘（哪类问题反响好）。
- 边界：同上，端点未探明，不要猜路径。

### 7. 小工具 `tools`（已开通，无契约）

- 现状：额度接口确认存在（**仅 10 次/天**），无契约。
- 推测能力（以黑客松能力表为准）：PDF 解析、知乎回答/文章生成 PPT。
- 对产品的价值（探明契约后）：本地 PDF 作为研究来源进入快照/引用体系；专题导出为演示文稿。
- 边界：额度极小（10 次/天），只适合用户显式触发的低频动作，绝不进自动链路。

### 8. 用户数据 `user_data`

五个端点，全部需要 OAuth token（`Authorization: Bearer <access_secret>` 代表调用方，个人请求另需会话 token，两种身份不可混用）：

| 端点 | 提供 | 关键边界 |
|---|---|---|
| `GET /api/v1/user/contents` 我的创作 | 内容列表（类型/标题/摘要/链接/点赞/评论/收藏数），支持按类型筛选、按时间或点赞排序、Offset 分页（Limit 最大 50） | 摘要不是全文 |
| `GET /api/v1/user/followees` 我的关注 | 关注的用户列表（昵称/主页/头像/一句话介绍/粉丝数），Offset 分页 | 只有关注列表，没有粉丝列表；不等于作者动态 |
| `GET /api/v1/user/favlists` 收藏夹列表 | 收藏夹元信息（名称/描述/UrlToken/是否公开） | **无分页**，不承诺遍历全部收藏夹 |
| `GET /api/v1/user/favlist_contents` 收藏夹内容 | 指定收藏夹内条目，Offset 分页，先取收藏夹拿 `UrlToken` 再查内容 | 游标完整性不保证 |
| `GET /api/v1/user/collections` 近期收藏 | 最近收藏的内容（含所属收藏夹、收藏时间、互动数），Limit 最大 50 | 只有近期列表，没有 Offset，**不是完整收藏历史** |

能做什么：资料库页（最近收藏、收藏夹导航、夹内多选加入专题）、"你的收藏夹里有相关资料"的规则关联、关注作者作为检索偏好线索、我的创作关联专题。

边界：所有列表都是"公开范围内"的数据；Int64 ID 必须按字符串保持精度；登出要同步清理个人缓存；性别等与任务无关的字段不进提示词。

### 9. 知识库 `knowledge`

| 端点 | 提供 |
|---|---|
| `GET /api/v1/knowledge/bases?Scope=all/created/subscribed` | 知识库列表（ID/名称/关系/内容数/更新时间），不分页 |
| `GET /api/v1/knowledge/bases/{ID}/items` | 库内内容列表，游标分页（Limit 1-20，`HasMore` 时才用 `NextCursor`） |
| `POST /api/v1/knowledge/search` | RAG 检索：指定知识库 ID 或范围（`personal`/`subscription`/`public`），Limit 1-10，返回有序片段数组 |
| `POST /api/v1/knowledge/files` | 上传单个文件（multipart，最大 100 MiB），可指定入库知识库 |

能做什么：个人知识桥——在用户明确选择的知识库范围内检索（研究结果与私人笔记对照）；把研究成果回存知识库；上传本地文档补充检索面。

边界：上传是有副作用的同步请求，**不自动重试**，超时后先查内容列表确认是否已入库；文件仍在处理（`40005`）时查询状态而不是重传；个人知识库检索结果默认短缓存，防跨用户污染。

### 10. 账号接入（OAuth）

- 授权页：`GET https://openapi.zhihu.com/authorize?redirect_uri=...&app_id=...&response_type=code`；回调带回 `authorization_code`。
- 换 token：`POST https://openapi.zhihu.com/access_token`。
- 提供：知乎账号登录、代表已授权用户调用个人数据接口、授权用户基础信息。
- 能做什么：「我的知乎」页的个人数据、收藏主链路、一切带用户身份的功能入口。
- 边界：`redirect_uri` 必须与登记地址完全一致（协议/域名/路径/尾部斜杠）；state、PKCE、刷新与撤销协议按契约联调；不接受前端任意 userId 作为授权凭证；服务端已实现授权跳转、令牌交换与会话管理，等 appID/appKey 发放后配置即可启用。

### 11. 额度查询

- 端点：`GET /api/v1/quota`，可选 `APIIDs` 过滤，查询本身不耗额度。
- 提供：各能力当日总额度、已用、剩余（`APIID/APIName/TotalQuota/TotalUsed/RemainingQuota`）。
- 能做什么：设置页的额度面板（把"今天还能用多少"透明地展示出来）、请求失败后判断是否额度问题、自动降档（搜索转直答 fast 档）的依据。
- 边界：不在每次业务请求前预检（浪费延迟）；不把历史邀测数字硬编码为运行时限制。

### 12. 赛事内容（黑客松专属）

- 端点：`GET /km-indep-home/hackathon/v2/story/list` 与 `/story/{work_id}`（故事）、`/knowledge/list` 与 `/knowledge/{work_id}`（知识），无需鉴权。
- 提供：赛事故事与知识内容的列表（`work_id`/标题/封面/简介/标签）与详情（章节名/作者/正文）。
- 能做什么：今日页的可选内容源、互动阅读场景；演示时的合规素材。
- 边界：**不是长期稳定承诺**，活动结束后路径和可用性可能变化；详情 ID 必须来自列表结果并做 path 编码；只访问文档列出的主机，不按返回内容切换域名；展示正文保留作者归属。

### 13. MCP 传输（可选）

- 搜索/热榜走 SSE 会话（`zhihu_search`、`global_search`、`hot_list` 三个工具），直答走 Streamable HTTP（`POST /api/mcp/zhida/v1/stream`）。
- 定位：与 HTTP 接口**同额度池、同数据**，只是另一种传输方式。产品主链路用 HTTP；MCP 返回的文本结果必须先转换为内部统一数据模型再使用，不产生第二套业务事实。

## 五、使用原则

1. **摘要不是全文**：搜索、热榜、收藏、创作列表给的摘要只用于展示和上下文，重要判断引导用户回原文核对；界面不得把摘要说成原文。
2. **无结果 ≠ 失败 ≠ 字段缺失**：三种状态分开表达，不能用空列表掩盖鉴权或协议错误。
3. **不编造热度与关联**：热榜没有热度值就不画热度；"与你有关"必须对应真实的规则命中或检索匹配。
4. **额度预算**：热榜（100/天）和小工具（10/天）最紧张，必须有共享缓存和用户显式触发；热榜的共享缓存与本地落盘已实现，主题检索按查询词做 15 分钟缓存并合并并发；搜索/直答（5000/天）宽裕但仍要做查询去重与 15 分钟级缓存。
5. **POST 不自动重试**：直答、知识库上传等有副作用的请求失败后由用户决定重试；幂等 GET 允许有限退避。
6. **个人数据最小读取**：只在用户明确进入相关页面时拉取，按会话用户隔离缓存，登出清理。
