# ADR-0010：个人档案（本地快照 + 规则组装）

日期：2026-09-13 · 状态：accepted（已实施，见[个人档案设计](../../design/个人档案设计.md)第 11 节）

## 背景

用户登录后当前只能看到个人创作、关注与收藏的**当前一页列表**：现有 `/api/user/*` 每个端点固定 `Limit=10`，`UserDataGateway` 也没有 Offset 分页（`src/platform/zhihu/user-data.ts` 的 `clampLimit` 只做单页请求）。用户明确希望做一类**只依赖用户个人信息组装**的功能，不依赖后端研究能力、不调用生成式模型。

同时需要澄清一个凭证边界：只用 OAuth token 时，平台仅开放 `GET https://openapi.zhihu.com/user` 一个端点；读取创作、关注、收藏必须同时携带 `Authorization: Bearer <access_secret>` 与 `X-OAuth-Token`。双头模型中 Access Secret 只标识应用调用方，**数据归属由 `X-OAuth-Token` 决定，不会读到凭证所属账号**，因此采用双头方式读取登录用户数据。

## 决策

1. 新增「个人档案」能力。数据源**只有**用户数据域的五类列表与 `/user` 基础资料；不调用知乎直答、搜索、热榜、知识库、小工具与问题推荐能力。
2. **采集与组装分离**：服务端按用户同步一份快照，快照是个人数据的唯一 owner；所有视图由纯函数从快照派生，派生过程零 IO、零额度、可单独测试。
3. 为 `UserDataGateway` 补齐基于 `Offset` 的分页；同步过程设页数上限、TTL 与并发合并，并以**用户稳定标识**（而非 access token）作缓存与落盘键。
4. 派生视图不产生新的业务事实，不引入第二套调度状态；`gender` 等与任务无关的字段不进入界面之外的任何用途。
5. 登出清理该用户的个人快照；鉴权失败时停止读取，不回退到凭证所属账号。

## 结果与取舍

- **额度可行**：`user_data` 为 10000/天，是全部能力中额度最宽的一项；一次全量同步约百次调用，规模可控。
- **能力边界**：不引入全文与模型，"立场档案""内容质量评价"一类能力仍不可做；界面只呈现摘要并引导回原文。
- **凭证依赖**：真实读取需完成公网 HTTPS 下的 OAuth 联调；接通前组装层可用 mock 数据独立验证。
- **身份依赖**：快照以 `/user` 的 `hash_id` 为稳定身份键；该端点无正式契约，取不到时降级为会话内临时档案（不落盘、登出即弃），并如实标注。
