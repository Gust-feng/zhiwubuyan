研究产品分四档（ADR-0007 最终定案）：**首页问答模式** `fast`（快速）/ `thinking`（深度思考），**深度研究** `pro`（直答检索增强）/ `ultra`（自研主管/并行单元架构）。产品只交付网页端，研究与凭证都由服务端承接（[ADR-0008](architecture/decisions/0008-web-only-server-hosted-research.md)）；研究引擎上传服务端尚未开始。Ultra 已通过一次真实端到端研究（completed + partial，127 findings / 227 来源 / 151 查询 / 192 模型推理）；快答档中 fast 与 pro（agent 模式）已真实调用成功，机制验证 14 项场景全绿；报告质量尚未人工评估，定向回查分支未在真实运行中触发过。tier 为创建请求必填字段，无隐式默认。

## 3. 运行架构

```
HTTP POST /api/research-tasks
  └─ engine.createResearchTask（requestId 去重 → 配置/繁忙检查 → 插入任务 → 派发）
       └─ port.startExecution(taskId)                     ← ResearchExecutionPort（src/agent 实现）
            └─ Mastra Workflow "deep-research"
                 ├─ plan        主管拆题（3–5 子问题，exploration 预算）
                 ├─ dountil(research-cycle)                         ← 最多 40 次迭代保护
                 │    ├─ decide        主管决策：research（≤3 单元 + planUpdates）或 synthesize
                 │    ├─ collect-units 把派发单映射为 foreach 输入数组（元素携带 taskId）
                 │    ├─ foreach(run-unit, concurrency 3)           ← 并行调查单元
                 │    │     预占额度 → 工具循环(search_zhihu/read_source[/search_web])
                 │    │     → 结构化 findings（失败时用本单元来源兜底整理一次）
                 │    │     → commitUnitFindings（逐条校验、剔除无效引用）→ 单元回执
                 │    └─ merge        主管合并：容错降级的覆盖判断 → analysis
                 ├─ write        Writer 产出四部分正文（只给 findingIds）
                 ├─ verify       确定性引用检查（write 内）→ Verifier 核验
                 ├─ repair       核验有问题且额度允许 → 一次定向回查单元
                 ├─ rewrite      按核验问题改写 → 重新确定性检查
                 ├─ reverify     强制复验（不能省略）
                 └─ save         finalizeReport：派生 sourceIds → 报告与 completed 原子提交
```

要点：

- **阶段投影**：公共 `stage` 只读投影自框架公开快照（`research-workflow.ts` 的 `projectStageFromState`），取值 planning / researching / writing / reviewing / repairing / saving / null。产品库不存可写 stage/status。
- **写许可**：一切写入（来源、发现、分析、报告）在产品事务内重查 `outcome IS NULL`；取消先把 outcome 设为 `cancelled` 关闭准入，再触发 `run.cancel()`。迟到的模型/搜索结果一律被拒绝或剔除，不报错中断。
- **停止判断**：应用拥有停止权（`evaluateExplorationEnd`），优先级为：覆盖完整 → 模型预算 → 搜索预算 → 时间进入收尾窗口 → 来源上限；主管 `synthesize` 与单元停滞保护（连续两批全失败且零发现）也触发收尾。没有固定轮数协议。
- **四档分档（ADR-0007）**：创建请求 `tier` **必填**（无隐式默认）。非 Ultra 档走 `runQuickAnswer`：同步调知乎直答（`TIER_ZHIDA_MODEL` 映射 fast/thinking/pro → 三个直答模型，pro 对应 `zhida-agent`），产物为任务上的独立 `answer` 对象，无来源无 findings，复用 requestId 幂等与 outcome；HTTP 语义为 200（已完成）/ 失败抛映射后的错误且任务记 failed。Ultra 由服务端承接（[ADR-0008](architecture/decisions/0008-web-only-server-hosted-research.md)）：创建时要求已配置研究模型（`MODEL_NOT_CONFIGURED` 503）与知乎凭证（`ZHIHU_NOT_CONFIGURED` 503）；原 `ULTRA_DESKTOP_ONLY` 桌面门禁与 `KANSHAN_EDITION` / `desktopEdition` 判定已撤销。

## 5. 数据与预算语义

### 5.1 产品库（`<dataDir>/product.sqlite`，WAL + foreign_keys）

| 表 | 关键列/约束 |
| --- | --- |
| `research_tasks` | `request_id UNIQUE`、`input_hash`、`outcome`(NULL/completed/failed/cancelled/interrupted)、`plan_json`（可变，version 递增）、`analysis_json`、`findings_json`、`query_log_json`（≤160 条准入记录）、`unit_receipts_json`（按 unitId 幂等）、`usage_json`、`limits_json`、`model_info_json` |
| `research_sources` | `UNIQUE(task_id, channel, identity, text_hash)`；`ON CONFLICT DO NOTHING`；写入前在事务内查 outcome 与 maxSources |
| `research_reports` | `task_id UNIQUE`（一项任务一份报告）；与 `outcome=completed` 同事务提交 |

### 5.2 预算账本（进程内，`deep-research.ts` 的 `ledgers` Map）

- **模型**：`admitModelSteps(taskId, n, phase)` 预占 → `onStepFinish` 逐推理步 `consumeModelStep` 结算 → `releaseModelReservation` 归还确定未用的预留。phase=exploration 上限为 `maxModelRequests - synthesisModelReserve`；synthesis 用到硬上限。**一次 generate 可能含多次推理，按步记账**（模型层 `maxRetries: 0`，另经 `[{model, maxRetries: 0}]` 关闭 provider 重试）。
- **搜索**：准入即计数（`searchRequests+1` 持久化），并发槽 `searchInFlight`（进程内，上限 4）；查询完成在 `settleQuery` 释放。重复查询（channel+规范化 text）复用已有来源或返回 `QUERY_IN_PROGRESS`。
- **单元**：预占 `unitMaxSteps`（12）次推理；工具循环失败时兜底整理再预占 3 次；结束时归还 `reserved - consumed`。单元本地额度：8 次搜索 / 5 分钟 / 12 步。
- **进程内状态**（预占计数、单元时钟、修复次数、探索停止原因）在重启后消失——重启的任务会先被标记 interrupted，不存在跨进程续跑，所以无需持久化。

### 5.3 容错语义（重要，改动前先读）

- `commitUnitFindings` **逐条校验、剔除无效**（unknown_question / no_evidence / unknown_source / quote_mismatch），返回 `{addedFindingIds, rejectedCount, rejectReasons}`；不再因单条失败抛错。
- `mergeUnitResults` **容错降级**：幻觉 findingId 被剔除；contested 少于 2 条依据降级 partial；supported 无依据降级 unanswered；模型遗漏的开放子问题补 unanswered 并写明缺口。不产生无依据的"支持"。
- 主管 decide / merge 阶段遇 `TIMEOUT`/`BUDGET_EXCEEDED`/`UPSTREAM_ERROR`：结束探索并如实记录 stopReason（`time_budget`/`model_budget`/`upstream_unavailable`），**不中断整项研究**——已有发现仍可成稿。写作/核验阶段的上游失败仍会任务失败（诚实路径）。
- `finalizeReport` 开头先查已有报告：产品已提交后框架迟到结果直接返回原报告。

## 5.4 内容数量限制的语义（重要）

模型输出 schema 里的数组类字段（findings、报告各段落、evidence 引用、核验 issues 等）**只设 500 条的反退化天花板**，用于兜底模型陷入重复循环的退化输出；正常研究的发现数与段落数不设预算，由内容决定。

超天花板时的行为是**截断保留**（`parseStageJson` 的 `truncateArrays`），不是整任务失败——这是修掉“丰富研究因段落超限而报告保存失败”的关键。其他结构错误（缺必填、ID 格式、类型不符）仍按 `MODEL_OUTPUT_INVALID` 处理：一次显式修正，仍失败则任务失败并保留材料。

早期实现曾把 findings 限 30、报告段落限 20 当作硬上限，导致 210 份来源的大规模研究在成稿阶段被拒绝。**不要重新引入按内容量收紧的上限**；若确需防退化，只调整这唯一的 500 天花板。

## 6. 已知问题与技术债（按影响排序）

1. **`MODEL_TIMEOUT_MS`（90 秒）已定义但未接线**。纯文本阶段与单元工具循环的模型调用只受"准入时"的剩余时间检查约束，没有单次调用的硬超时 abort。一个卡住的模型请求最长可拖到任务级 deadline。接法：在 `research-agent.ts` 的两处 `generate` 上组合 `AbortSignal.any([args.signal, AbortSignal.timeout(MODEL_TIMEOUT_MS)])`（搜索侧已是这个模式）。
2. **模型可能在报告正文 text 里内联 `finding-xxx` ID**。Writer 提示词已禁止，但修正后未重跑真实研究验证。若复现，可在 `finalizeReport` 派生段落时对 text 做一次 `finding-\w+` 模式清理或退回修正（注意：这是展示层清理，不得改变引用归属）。
3. **`ResearcherOutput.findings` schema 上限 30**，应用未按方案裁剪到 10。超 30 仍会 MODEL_OUTPUT_INVALID（有兜底整理），30 以内全量提交。若要严格执行"最多 10 条"，在 `runOneUnit` 提交前 slice 即可。
4. **回查分支未实测**。`repair → rewrite → reverify` 的代码存在且通过机制检查，但真实运行中 Verifier 未报出触发回查的问题。验证方法：临时调低 `WRITER_SYSTEM` 质量或在 fixture 中让 Verifier 返回 issues，观察 repair 单元是否启动、预算是否计入、复验是否执行。
5. **`projectStageFromState` 的 researching 粒度**：主管决策与单元执行在框架快照里都表现为 `research-cycle` 运行中，投影统一为 `researching`（旧设计的 searching/analyzing 细分已随轮次模式移除，符合现行 API 文档）。
6. **Token 计量在并行单元间非精确对账**：`onStepFinish` 异步结算 + finally 归还存在窗口，极端情况下归还数可能略有偏差（保守方向：少归还）。影响仅限 usage 展示，不影响硬上限准入（准入时以已结算数+预占数判断，宁可拒不可超）。

## 8. 踩坑记录（环境与框架，改代码前先读）

1. **Node 直接跑 TS 只支持 strip 模式**：`node src/**.ts` 不支持构造函数参数属性（`constructor(readonly x)`）。项目内已全部改为显式字段（见 `ResearchApiError`/`StageFailureError`/`StorageError`/`ResearchStore`）。新代码不要引入参数属性。
2. **本机 TLS**：访问模型端点曾出现 `SELF_SIGNED_CERT_IN_CHAIN`。启动命令带 `--use-system-ca`（Node 24，仅追加系统根证书）。不要用 `NODE_TLS_REJECT_UNAUTHORIZED=0`。
3. **proper-lockfile 的锁目录**：加锁前必须 `mkdirSync(dataDir, {recursive: true})`（`acquireDataDirLock` 已处理）。强杀进程会留下锁文件，`stale: 60_000` 窗口内第二次启动会报 "Lock file is already being held"——等待或手动删除 `<dataDir>/backend.lock`。
4. **libsql 句柄**：Windows 下连接关闭后文件锁释放有延迟；测试脚本 `rmSync` 临时目录可能 EPERM，验证脚本已做成 best-effort。
5. **DeepSeek（deepseek-flash）**：不支持原生 `response_format`（400 "This response_format type is unavailable now"）；Mastra `structuredOutput` 走 fallback 有隐式二次调用风险，因此**全部阶段用 plain generate + 自行 JSON 解析**（`parseStageJson`）。模型会输出 rich 但不合 schema 的 JSON（如 `sub_questions`），所以提示词里放了精确 JSON 模板；模型输出 schema 用宽松剥离而不是 strict。
6. **Mastra 1.66 API 事实**（实测）：`createStep` 用 `retries: 0`，`createWorkflow` 用 `retryConfig: {attempts: 0, delay: 0}`；`Mastra` 构造器没有 `autoRestartActiveRuns`（放在 workflow `options` 里）；generate 级没有 `tools`（用 Agent 构造器 `tools` 的 DynamicArgument 形式 + `requestContext` 传单元身份）、没有 `maxRetries`（用 `model: [{model, maxRetries: 0}]`）；`foreach(step, {concurrency: n})` 要求前一步输出是数组；`getStepResult(嵌套workflow)` 可取循环体输出。`workflow.getWorkflowRunById` + `createWorkflowStateReader` 是公开状态读取入口。
7. **Bash heredoc 写代码的转义陷阱**：向 TS 文件写入含 `\n` 的字符串字面量时，shell/python 转义容易把字符串拆成真实换行导致 "Unterminated string literal"。遇到多行字符串修改，优先用 Edit 工具；用脚本时避免在替换文本里携带转义序列。
8. **轮询脚本别用裸 `while` 前台跑**：长任务监控放后台任务或分次 `sleep` + `tail`，避免超时。

## 9. 未完成与建议下一步

按价值排序：

1. **报告质量人工评估**：抽查真实报告的引用支持率（目标 ≥90%）与覆盖评分；用 `docs/research/quality-cases.md` 的 Q01/Q03/Q08 三个问题各跑一次并记录。质量证据当前为零，这是发布前最大的缺口。
2. **接线 `MODEL_TIMEOUT_MS`**（第 6 节第 1 条，约 10 分钟改动 + 一次真实运行验证）。
3. **实测回查分支**（第 6 节第 4 条）：确认 repair 单元的预算归属、复验执行、以及"无回查额度时删除/弱化断言"的降级路径。
4. **验证 Writer 修正**（第 6 节第 2 条）：重跑一次真实研究，确认正文不再泄漏内部 ID；若泄漏，在 `finalizeReport` 加展示层清理。
5. **`closeQuestions` 真实触发验证**：本轮真实运行以来源饱和收尾，主管关闭子问题的路径未观察过。
6. **并发搜索槽压测**：`searchInFlight` 上限 4 的行为只在机制脚本里覆盖过。

- 仓库有大量未跟踪文件（整个 `src/`、`docs/` 等），**没有提交任务授权，未做任何 commit/push**。
- `src/` 中同时存在研究后端（本文所述）与旧原型（`src/application/runtime.ts`、`research-session.ts`、`research-brief.ts`、`src/workbench/`），互不依赖对方内部实现；`pnpm verify:mvp` 保护旧原型行为。`src/desktop/` 是已冻结的 Electron 壳（产品只交付网页端，见 [ADR-0008](architecture/decisions/0008-web-only-server-hosted-research.md)）。
- 数据目录 `data/`（默认）与 `tmp/` 不应进入版本库；`.env` 已在 `.gitignore`。
- 模型密钥只存在于 `.env` 与进程内存；任何日志、错误 details、导出文件都不应出现它。若在输出中发现密钥形态的字符串，立即视为泄露处理。
