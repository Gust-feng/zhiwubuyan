# 个人档案设计

日期：2026-09-13 · 状态：**已实施**（S1–S6、接线与前端均完成，见第 8 节）。决策见 [ADR-0010](../architecture/decisions/0010-personal-archive.md)。

本文描述「个人档案」：把登录用户自己的创作、收藏与关注，组织成几个**只做规则组装**的视图。数据源只有用户数据域与 `/user` 基础资料；不调用直答、搜索、热榜、知识库、小工具与问题推荐。组装过程不依赖模型，也不读正文全文。

## 1. 定位与边界

| 项 | 结论 |
|---|---|
| 数据来源 | `/api/v1/user/contents`、`/api/v1/user/followees`、`/api/v1/user/favlists`、`/api/v1/user/favlist_contents`、`/api/v1/user/collections`；`GET openapi.zhihu.com/user` |
| 鉴权 | Access Secret + `X-OAuth-Token` 双头；归属由 OAuth token 决定 |
| 额度 | 仅 `user_data`（10000/天）；`/user` 不计额度 |
| 计算 | 集合运算、时间分桶、URL 解析、字符串规则；**无模型调用** |
| 产物 | 采集 → 快照（持久化）；视图（派生，不持久化） |

明确不做，且不因后续迭代放开：正文全文、立场归纳、内容质量评分、粉丝与涨粉、关注动态流、收藏夹写回。

## 2. 额度与同步策略

### 2.1 成本核算

单次全量同步按下表估算，页大小取 50：

| 数据 | 典型量 | 调用数 |
|---|---:|---:|
| 创作 | 500 | 10 |
| 关注 | 300 | 6 |
| 收藏夹列表 | 30 | 1 |
| 收藏夹内容 | 30 夹 × 1 页 | 30 |
| 近期收藏 | 1 | 1 |
| **合计** | | **≈ 48** |

重度用户（创作 5000）约 100 页 + 收藏夹页，仍在 200 次以内。10000/天 对单账号留出充足余量；但额度**按 Access Secret 所属账号汇总、多用户共享同一池**，因此必须"一次同步、多次组装"，不允许每次进入界面都全量扫描。

### 2.2 同步规则

- **显式与节流**：只在用户进入个人档案时触发，配 TTL（默认 12 小时）；未过期直接读快照。提供"重新同步"手动入口。
- **并发合并**：同一用户并发进入只发一次上游请求，沿用 `src/application/question-recommendations.ts` 已验证的 `Map` 缓存 + `inFlight` 合并范式，不另造机制。
- **增量**：创作按 `SortField=ts&SortOrder=desc` 翻页，遇到已存在于快照的 `Url` 即停；单集合设页数上限（默认创作 20 页、关注 10 页），到顶即停并记录 `truncated`，不静默假装完整。
- **游标**：`Paging.NextOffset` 是字符串，按整数解析后回传；解析失败报协议错误（`PROTOCOL_ERROR`），不静默截断。
- **身份键**：用 `/user` 的 `hash_id`；取不到时该次同步不落盘，仅会话内存活，界面标注"本次为临时档案"。

## 3. 三层结构

```text
① 采集同步（application/personal-archive.ts，有副作用，耗 user_data）
        ↓ 落盘
   快照（storage/personal-archive-store.ts，唯一 owner）
        ↓
② 组装（application/personal-archive-views.ts，纯函数，零 IO）
        ↓
③ 呈现（workbench 视图块，复用现有加载形态）
```

- 第①层只负责"把当前登录用户的个人数据取全并保存"，不计算视图。
- 第②层是产品价值所在：输入快照，输出视图 DTO；不读写任何外部状态，可单元测试。
- 第③层挂在现有 `MinePage` 分区体系内，不新建路由框架；数据经 `use-core-feed` 同构的加载态呈现。

## 4. 数据契约

快照为有类型 JSON，schema 由 storage owner 定义，含版本号：

```text
PersonalArchiveSnapshot
  schemaVersion   整数
  userIdHash      字符串    // /user 的 hash_id；稳定身份键
  syncedAt        字符串    // ISO 时间
  profile?:       { fullname, avatarUrl?, headline? }
  creations:      CreationItem[]     // 复用 platform 已有 DTO
  followees:      FolloweeItem[]
  favlists:       FavlistItem[]      // 名称/描述/UrlToken/IsPublic
  collections:    CollectedItem[]    // 近期收藏（非完整历史）
  truncated:      { creations?: bool, followees?: bool, favlistContents?: bool }
```

视图 DTO（第②层产物，不落盘）：

```text
QuestionCluster    { questionId, questionUrl, creationItems, collectionItems, total }
CreationYear       { buckets: { date, count, byType }[], streakDays, longestStreak }
ResponseStructure  { url, title, likeCount?, commentCount?, favoriteCount?, label }
CollectionTimeline { buckets: { period, items }[], dormant: CollectedItem[] }
FolloweeTier       { tier, items: FolloweeItem[] }
HeadlineKeywords   { keyword, count, sampleNames }
```

## 5. 视图设计

### 5.1 同题聚合（主打）

- **来源**：快照的创作与收藏。
- **规则**：从 `Url` 抽出 `zhihu.com/question/{qid}`；按 `qid` 分组；只保留组内条目数 ≥ 2 的组。
- **呈现**："这个问题下你收藏了 5 个不同说法""这题你答过，还收藏了 3 篇"。
- **价值**：唯一真正体现"组装"的动作，纯正则与分组，零模型；可一键作为研究 / 众声的输入。
- **边界**：只依据 URL 是否同题，不断言用户立场或偏好。

### 5.2 创作年轮与反响结构

- **来源**：快照的创作（`CreatedAt`、`ContentType`、互动数）。
- **规则**：按日期分桶出日历热力图与连续创作天数（streak）；按 `like_count` 排序出反响榜；每篇按 赞/评/藏**比值**打结构标签（评论占比偏高记为"讨论型"，收藏占比偏高记为"参考型"）。
- **边界**：标签是**比例描述**，不是质量评价；不得写成"最好的内容"。

### 5.3 收藏时间线与沉睡收藏

- **来源**：快照的近期收藏（`FavTime`）。
- **规则**：按周/月分桶；`FavTime` 早于 N 天（默认 30）的条目归入"沉睡收藏"。
- **边界**：没有浏览数据，只能表述"收藏超过 N 天"，**不得**说"你一直没看过"；`collections` 非完整历史，视图如实标注覆盖范围。

### 5.4 关注圈层

- **来源**：快照的关注（`FollowerCount`、`Headline`）。
- **规则**：按粉丝数分"大 V / 同行 / 小众"三档；`Headline` 做简单关键词统计（不调模型）。
- **边界**：口径是"关键词命中 / 粉丝数分层"，**不得**包装成"懂你的圈子"或个性化画像。

## 6. 身份、缓存与失败

- 快照与缓存**按用户隔离**，键含用户稳定标识；不与公共数据共用缓存。
- 登出同步清理该用户快照与内存缓存。
- 鉴权失败（`AUTH_INVALID`）时销毁会话并要求重新登录，不回退到凭证所属账号。
- 沿用既有产品错误码：`AUTH_REQUIRED`、`AUTH_INVALID`、`RATE_LIMITED`、`QUOTA_EXHAUSTED`、`UPSTREAM_ERROR`、`PROTOCOL_ERROR`。
- 空列表是正常空数据，不算失败；失败、空结果、字段缺失三种状态分开表达，不用空列表掩盖鉴权或协议错误。

## 7. 前置改动

1. **`UserDataGateway` 补 Offset 分页**：现有 `clampLimit` 只发单页请求，需增加 `offset` 入参并在应用命令内驱动翻页。
2. **新增快照存储**：`src/storage/personal-archive-store.ts`，定义 schema 与按用户隔离的读写。
3. **新增应用命令**：`src/application/personal-archive.ts`（采集）与 `personal-archive-views.ts`（组装）。
4. **前端接线**：在 `MinePage` 分区中新增视图块，复用 `use-core-feed` 加载形态。

## 9. 验收

- 进入个人档案不重复消耗额度：TTL 内多次进入只读快照；并发进入只发一次上游请求。
- 截断被如实标注：达到页数上限时视图说明覆盖范围，不显示为完整列表。
- 组装视图全部有纯函数单测；同题聚合覆盖"同题多条 / 跨题 / 单条不聚合"。
- 登出后该用户快照与缓存被清理，不残留。
- 界面措辞符合各自边界（比例描述、关键词命中、收藏天数），不出现质量评价或画像式断言。
- 类型检查、构建通过，`git diff --check` 无告警。

## 10. 依赖与风险

- 真实读取依赖公网 HTTPS 下的 OAuth 联调；接通前 S1–S6 可用 mock 上游完成，组装层不依赖线上凭证。
- `/user` 无正式契约，`hash_id` 取不到时降级为会话内临时档案。
- 额度为账号级共享池，多用户场景需按 TTL 与并发合并控制总消耗；后续如需扩大并发用户，应评估独立凭证或降低同步频率。
- **网页端（Vercel）不落盘快照**：serverless 无持久文件系统，该入口只创建进程内缓存。实例间不共享，因此同一用户可能在不同实例各同步一次；TTL 只在本实例内生效。本地运行面通过 `local-server.ts` 注入文件存储，行为与本文一致。如需网页端也保证全局唯一同步，需要共享 KV，与登录会话/限流使用同一份 KV 是自然落点。

**实施中对设计的修正**

- **创作年轮改为固定 365 天连续窗口**（含零值日、按星期对齐）：只输出有创作的日期会让相邻格子把「隔了三天」画成「连着两天」，属于视觉层面的不实呈现。窗口外的创作只进统计、不入图。
- 采集不做「遇到已存在 Url 即停」的增量短路：首次同步无基线，且收藏夹内容需逐夹遍历才能得到完整图；增量改为由 TTL 与手动 `refresh=1` 控制，语义更简单且不会因短路漏掉新夹。
- `collections` 的 `FavTime` 缺失时保持缺省而非回填抓取时间，避免旧收藏被显示成「刚收藏」。
- 前端按分区懒加载：打开「我的知乎」看笔记不会触发同步，只有进入个人档案才取数。视图实际为四组（同题聚合 / 创作年轮含反响结构 / 收藏时间线 / 关注圈层含关键词），与第 5 节一致。

**验证结果**

- `pnpm typecheck`（root + workbench + backend）通过；工作台 `vite build` 通过。
- `verify:archive` 两个脚本通过：组装规则（同题去重/阈值、年轮窗口与 streak、比值标签、时间线与沉睡、粉丝分层、关键词）、采集（分页、上限、TTL 复用、并发合并）、存储（隔离、非法键、清理）、端到端（路由、五视图、缓存、refresh、登出清理、未登录 401）。
- 浏览器实测：以模拟档案数据驱动，四个视图正确渲染，日历按周对齐。

**未验证部分**：真实知乎账号的 OAuth 联调仍未进行（依赖公网 HTTPS 部署），因此上述验证覆盖产品行为与规则，不代表真实账号数据的端到端结果。
