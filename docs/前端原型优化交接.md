# 前端原型优化交接（给协作 Agent）

> 面向对象：在独立环境中接手「看山工作台」前端原型、负责界面与体验优化的协作 Agent。
> 你的任务：优化这份前端原型的界面与体验。具体优化重点见第 9 节（需求方可增补）。
> 本文自包含运行方式、代码地图与必须遵守的设计/语言规则。若你同时拿到了仓库 `docs/` 下的《核心布局设计》《语言体系设计》《架构基线》，以原文为准，本文是摘要。

当前界面优化以[工作台核心布局设计](design/核心布局设计.md)为唯一布局维护入口。首页内容流、独立发现入口、板块职责与扩展规则按该文档执行；本交接中的代码地图描述现状，不代表页面已完成改造。

当前后端只交付 Mastra 深度研究，范围见 [ADR-0005](architecture/decisions/0005-deep-research-mvp-scope.md)，运行契约按 [ADR-0006](architecture/decisions/0006-supervised-research-runtime.md)。计划随证据变化，UI 只读展示 version 与子问题，不提供用户编辑；阶段可出现 researching 和 repairing。对接按[接口文档](backend-api.md)和[契约样例](research/contract-examples.md)：共享 Zod 产品 DTO，前端不导入框架或自行调度研究步骤。前端其他页面可继续独立开发，不把其平台接口要求加回研究任务。

研究交互为提交问题后自动规划与执行，约每 1–2 秒轮询，支持取消、读取来源和已保存报告。当前不展示可编辑计划、暂停/继续或版本控制；来源明确标为搜索摘要，不能用示例数据兜底真实接口失败。开发细节见[方案第 8 节](deep-research-development-plan.md#8-http-与后端运行)。

## 1. 产品是什么

- 产品名：**知无不言**——围绕知乎公开内容与个人知识构建的**本地知识研究工作台**。
- 普通简报链路：提出问题 → 检索知乎/全网/热榜来源 → 用户筛选来源 → 生成带编号引用的研究报告 → 随研究任务或用户知识空间沉淀。
- 深度研究链路：提交问题与来源选项 → 自动规划和分轮取证 → 轮询进度与缺口 → 读取已保存报告。研究独立于普通简报，当前不要求先建设成果版本库。
- 三条产品原则（决定一切界面取舍）：
  1. **问题先于答案**——页面主语是问题本身，不是 AI；
  2. **观点必须有来路**——来源行永远携带作者、类型、域名，结论紧挨编号引用；
  3. **AI 住在阅读里，不盖住阅读**——AI 是状态表达（找到资料 → 你来筛选 → 我来整理），不是常驻聊天窗。
- **看山**是产品的 AI 助研角色。性格：诚实、扎实、克制；不替用户下结论、不编造。
- 品牌口径：窗口标题「知无不言工作台」，界面品牌「看山工作台」，本地数据键前缀 `kanshan/workbench-v1:`。
- 运行形态：本地 Web 与 Windows 桌面壳（Electron 加载同一套静态构建）。桌面壳通过 `window.desktopHost` 提供少量原生桥（如本地偏好读写），所有调用都带浏览器回退，**纯浏览器环境可完整运行**。

## 2. 你应该拿到的文件（先自检）

前端原型 = `src/workbench/` 整个目录 + 根目录四个文件：

```
src/workbench/              # 前端源码（src/、api-contracts/、demo/ 等）
vite.config.workbench.ts    # 独立构建配置
tsconfig.workbench.json     # 独立类型检查配置
package.json                # 依赖清单
pnpm-lock.yaml              # 锁定版本
```

缺 vite/tsconfig/package.json 时构建与依赖装不起来，先向提供方索要。仓库里另有 `src/server` 本地 API 可供联调；`src/web`、`src/web-redesign` 两套旧前端不在本次范围内，可忽略。

## 3. 运行与验证

环境：Node.js ≥ 22.6.0，包管理器 pnpm。

```bash
pnpm install
pnpm dev:workbench                                   # 开发服务器 → http://127.0.0.1:4303
pnpm exec tsc --noEmit -p tsconfig.workbench.json    # 仅工作台的类型检查
```

- 原型阶段**不需要任何后端和凭证**：`vite.config.workbench.ts` 里的 demoEntryPlugin 把入口换成 `src/workbench/demo/main.ts`，它先安装示例传输层（拦截 `window.fetch` 与 `EventSource` 的 `/api/*` 请求，返回 `demo/fixture.ts` 内置数据），再加载正式入口 `src/main.tsx`。界面全部功能可浏览、可交互。
- 接真实后端时按接口文档同步 schema、API client、状态和事件，再显式关闭 demoEntryPlugin；不承诺零改动。示例逻辑集中在 demo 层，真实错误或空结果不能回退示例。
- 已知坑：dev server 的 proxy 必须写正则 `"^/api/"`，不能写前缀 `"/api"`，否则源码模块路径 `/api-contracts/*` 会被误代理导致白屏。

## 7. 文案规则（改任何一句界面文案前必读）

产品名「知无不言」是一条可执行的语言契约，两条行为准则：

1. **知无不言（说不说）**：检索到的相关信息不回避；没检索到、没依据的直接说"没有查到"，不编造听起来合理的答案。
2. **言无不尽（说多细）**：给结论同时给支撑证据、不同声音和局限性；"尽"是信息完整度，不是字数或修辞。

写文案自查：

- 区分"来源里说的"和"看山的整理判断"，两者不能混在一句里；
- 摘要不能说成原文；涉及结论的页面要有"回到原文核对"类提示；
- 不确定性用词：「目前查到的是……」「这些来源里……」「这是我的整理，不代表结论」；禁用「显然」「毫无疑问」「众所周知」（除非来源原文如此且已标注引用）；
- 禁用营销词（颠覆、革命性、一站式、干货满满）与 AI 免责套话（"作为一个 AI，我不能……"→ 换成具体边界说明）；
- 语气：对事实自信、对推断谦逊；偏口语但用词精确；不用「亲/您」、不说教、不卖萌、默认不用表情符号；
- 等待与错误语言：说"正在做什么"而不是转圈；出错先说明"不是你的操作有问题"，再说"接下来能做什么"；不向用户暴露错误码；
- 示例数据必须标注「设计示例/非真实来源」，与真实结果措辞可区分——原型阶段全部数据都是示例，涉及将来真实数据的文案要注意这一点；
- 界面自称：AI 角色用「我」或「看山」，对用户统一用「你」。

## 8. 工程约束

- `api-contracts/` 及其依赖闭包（domain/、kernel/、text-projection/ 等）是前后端共享契约，是未来接真实接口的对接口。本次优化**不改契约形状**；若优化确实需要新数据，先在 demo 层扩展，并把需要的契约变更单独列出来交回，不要顺手改类型。
- 单一事实 owner：同一业务状态不在多个模块各存一份；跨模块行为走显式入口，不复制规则。
- 命名用稳定领域词，不用页面临时名或接口路径名；最小改动，不顺手重构无关代码。
- 凭证与密钥永远不进前端：原型阶段不实现任何凭证、token、代理逻辑。
- 按变更风险运行针对性的类型检查、受影响构建与 `git diff --check`。文档改动检查链接和一致性；只有需要验证布局或交互行为时才做定点 UI 检查，不默认运行全量测试。
- 项目材料（代码注释、文档、提交信息）只描述本项目自身的需求与实现，不引入其他工程的名称、路径或内部术语。

4. 当前优化按[核心布局设计第 8 节](design/核心布局设计.md#8-实施顺序与验收)分阶段推进：入口与边界、首页内容流、发现与搜索、对象衔接、后续板块。文档已明确方向，页面与真实能力分别验收。
